## 로컬 운영

로컬 MCP 프로세스를 중지한 뒤 메타데이터 전용 SQLite 장부와 설정을 백업합니다. 한도를 풀기 위해 기록·unknown 예약을 삭제하거나 열린 장부를 실시간 동기화하지 마세요. API 키는 SQLite가 아닌 선택한 자격증명 backend에 남습니다. SIGTERM은 진행 중 작업을 중단하고 불확실한 상태를 기록한 뒤 닫으려 시도하지만 크래시·SIGKILL·네트워크 단절은 reserved를 남길 수 있습니다. 원래 ID로 조회하며 재실행하지 않습니다. rebut remove는 등록만 제거하고 장부나 자격증명을 삭제하지 않습니다. 아래 D1 운영은 Worker 모드용입니다.

## Worker


Cloudflare가 지원하는 내보내기·Time Travel 방식으로 메타데이터 전용 D1 원장을 백업하세요. 대기 중인 요청을 없애기 위해 원장을 삭제하지 마세요. 지출 기록과 중복 방지 기능이 사라집니다. 클라이언트가 ID를 재사용할 수 있는 동안 요청 행을 보존하세요. 행을 정리하면 오래된 ID로 다시 실행할 수 있게 됩니다.

원래 인증 주체에서 `rebut status REQUEST_ID`로 무료 메타데이터를 조회합니다. `rebut doctor`는 민감한 값을 제거한 로컬 설정과 자격증명 사용 가능 여부를 확인하고 `rebut doctor --connect`는 무료 원격 `tools/list` 확인을 수행합니다. 이 명령들은 유료 검토를 시작하지 않습니다. 불확실한 결과 뒤에도 요청 ID와 예약을 보존하세요.

소유자 프로필 변경은 리비전을 사용합니다. `409` 충돌 뒤에는 `rebut profile list`를 다시 읽고 수정·제거 여부를 판단하세요. 제거는 비활성화 tombstone을 남깁니다. 기존 요청은 프로필 변경 뒤에도 원래 모델·리비전, 인증 주체별 ID, 예약을 유지합니다. 자동 재실행·환불·예약 해제는 없습니다. 일회성 Worker 업그레이드, D1 마이그레이션 `0002`, `ADMIN_TOKEN_SHA256` 설정 후 프로필 변경은 D1 기록만 필요합니다. 별도 관리자 bearer를 Codex/MCP 설정에 넣지 마세요.

## 시간 초과, 연결 끊김, unknown

`reserved`는 실행이 예약되었으며 아직 실행 중이거나 중단되었을 수 있음을 뜻합니다. 과금되지 않은 실패의 증거가 아닙니다. `unknown`은 결과나 사용량을 확인할 수 없음을 뜻합니다. 두 상태 모두 자동 재시도, 만료, 환불을 하지 않습니다. 검토할 때까지 무기한 동시 실행 슬롯을 차지합니다. 실행을 대조하여 확인할 수 없을 때 추가 지출을 의도적으로 막는 동작입니다.

1. 원래 요청 ID, 인증 주체, 입력 해시, 프로필, 공급자 ID(있는 경우)를 유지합니다.
2. 해당 인증 주체로 `review_status`를 조회합니다. 전송 실패 후 `not_found` 응답만으로는 새 ID를 제출할 충분한 근거가 되지 않습니다. 먼저 서버 처리와 원래 요청을 대조하여 확인하세요.
3. 공급자 프로젝트 사용량과 요청 진단 정보를 비교합니다. `store:false`를 사용하면 응답 조회가 불가능할 수 있습니다. 검토를 다시 제공한다는 보장은 없습니다.
4. 독립적인 근거가 있는 운영자만 정확한 `(principal, request_id)` 행을 수정해야 합니다. 신뢰할 수 있는 사용량 근거가 다른 요금을 입증하지 않는 한 과금·예약 금액을 보존하고, 대조가 끝난 최종 상태를 설정합니다. 애플리케이션은 초기화·환불·삭제 도구를 제공하지 않습니다. 근거를 비공개로 기록하세요. 실행 결과를 알 수 없는 요청을 새 유료 호출로 몰래 바꾸지 마세요.

예약은 대조 및 정리 후에도 원래 제출한 UTC 날짜·월에 귀속됩니다. 날짜와 월이 바뀌어도 unknown 상태의 동시 실행 점유는 초기화되지 않습니다. 요청 금액은 일·월 합산 한도의 남은 금액을 초과할 수 없습니다. 요청 속도 제한은 무료 메타데이터 호출이 아닌 새로 예약된 검토 ID에 적용됩니다(예시에서는 하루 100개). 필요하면 앞단에 네트워크 수준의 남용 방지 장치를 두세요.

## 업그레이드

`npm ci`, 타입 검사, 빌드, 테스트를 실행합니다. 먼저 마이그레이션 SQL을 검토한 다음 같은 D1 데이터베이스에 새 마이그레이션을 적용하고 비공개 설정으로 배포합니다. 기존 `(principal, request_id)` 행은 업그레이드 후에도 보존해야 합니다. 허용 목록의 프로필을 바꾸어도 완료된 ID를 다시 실행하지 않습니다. 대조 및 정리가 끝난 뒤 의도적으로 새 검토를 시작할 때만 새 ID를 사용하세요. 인증 주체 ID를 바꾸면 기존 상태 행에 접근할 수 없으므로 bearer 토큰을 교체할 때도 ID를 안정적으로 유지하세요.

## 교체 또는 제거

토큰을 교체하려면 새 무작위 값을 생성하고 `AUTH_TOKENS`에서 해당 인증 주체의 다이제스트를 바꾼 뒤, 허가된 클라이언트의 비밀번호 관리자 기반 설정을 갱신합니다. 단순한 토큰 교체를 위해 인증 주체 ID를 바꾸지 마세요. OpenAI 키는 `OPENAI_API_KEY`만 갱신하여 교체합니다. 공유 키를 사용하는 다른 주체와는 별도 조율이 필요합니다. 새 요청을 중단하려면 Worker를 삭제합니다. D1을 별도로 제거하기 전에 원장을 내보내고 검토하세요. 삭제는 되돌릴 수 없으며 중복 방지 이력을 사용할 수 없게 됩니다.

## 로컬 복구와 제한된 용량 추가

1. MCP 호스트를 중지하고 `rebut status REQUEST_ID`로 원래 요청을 확인합니다. 재전송하지 마세요.
2. 닫힌 로컬 장부와 설정을 백업하고 가능한 공급자 근거를 검토합니다. budget_reserved_microusd·budget_accounted_microusd는 앱 회계값이며 unknown의 실제 청구액 확인값이 아닙니다.
3. 실행이 불확실하면 행·전액 회계 예약·원래 ID를 유지합니다. 미청구로 간주하거나 삭제하거나 완료 결과를 만들지 않습니다.
4. 이 회계 예약을 유지하기로 명시적으로 판단한 운영자는 의도적인 새 검토를 위한 용량을 추가할 수 있습니다. 불확실한 요청 한 건이 기본 한 슬롯을 점유하면 `rebut set max-concurrent 2`로 한 슬롯을 추가합니다(범위 1–10). 기존 슬롯 해제·환불·원래 입력의 재시도 허가는 아닙니다.
5. MCP 호스트를 재시작합니다. 일·월·요청 한도는 전체 회계 사용량에 계속 적용됩니다. 실제 장부 정산에는 독립 근거와 해당 행에 대한 운영자 검토가 필요하며 자동화하지 않습니다.

ID를 잃었다면 `rebut status --pending`부터 실행하세요. 키·공급자 호출 없이 로컬 reserved/unknown 메타데이터를 최대 100건 나열하고 추가 건은 has_more로 표시합니다. 진단 스냅샷이며 새 유료 호출의 허가가 아닙니다. 대기 행이 없어도 금액·일일 요청 수 한도 때문에 limit_exceeded가 나올 수 있습니다.

용량 상한은 10입니다. 전부 불확실하면 기록 삭제나 미청구 간주 대신 근거 기반 운영자 정산까지 중지합니다. 독립 근거로 정산한 뒤에는 임시 용량을 의도한 정상값(기본 1)으로 낮추고 재시작하세요.

기존 사용자 지정 한도에 예시 2를 그대로 덮어쓰지 말고, 대기 건수와 의도한 신규 동시 실행 수를 더해 용량을 선택하세요(최대 10). 용량·예산 명령은 로컬 한도 전체 스냅샷을 보존합니다. 원래 ID가 없으면 1단계 전에 status --pending을 실행하세요.
