## ローカル運用

ローカルMCPプロセスを停止してからメタデータ専用SQLite台帳と設定をバックアップします。制限解除のため履歴／unknown予約を削除したり開いた台帳を同期したりしません。APIキーはSQLiteではなく資格情報backendに残ります。SIGTERMは中断と不確かな実行の記録後に閉じようとしますが、クラッシュ・SIGKILL・切断でreservedが残る場合があります。元IDで照会し再実行しません。rebut removeは登録のみを削除し、台帳やキーは削除しません。以下のD1運用はWorker専用です。

## Worker

Cloudflare がサポートするエクスポートや Time Travel の仕組みを使い、メタデータのみの D1 台帳をバックアップしてください。保留中のリクエストを解消するために台帳を削除しないでください。支出管理と重複防止が失われます。クライアントが ID を再利用する可能性がある期間は、そのリクエスト行を保持してください。行を削除すると、古い ID が再び実行可能になります。

元のプリンシパルで `rebut status REQUEST_ID` を使い、無料でメタデータを照会します。`rebut doctor` は機密値を除いたローカル設定と認証情報の利用可否を確認し、`rebut doctor --connect` は無料でリモートの `tools/list` を確認します。これらは有料レビューを開始しません。不確かな結果の後もリクエスト ID と予約を保持してください。

所有者のプロファイル変更はリビジョンを使います。`409` の競合後は `rebut profile list` を読み直し、更新・削除を判断してください。削除は無効化する tombstone を残します。既存のリクエストはプロファイル変更後も元のモデル・リビジョン、プリンシパルごとの ID、予約を保持し、自動再実行・返金・予約解放は行いません。一度限りの Worker 更新、D1 マイグレーション `0002`、`ADMIN_TOKEN_SHA256` 設定後は、プロファイル変更は D1 書き込みだけです。別の管理 Bearer を Codex/MCP 設定に入れないでください。

## タイムアウト、切断、結果不明

`reserved` は、実行が予約され、まだ実行中か、中断された可能性があることを意味します。課金されなかった失敗の証拠ではありません。`unknown` は、結果または使用量を確認できなかったことを意味します。どちらの状態も自動で再試行、期限切れ処理、返金されません。確認されるまで、どちらも無期限に同時実行枠を占有します。実行を照合できない場合に、追加支出を意図的に停止する仕組みです。

1. 元のリクエスト ID、プリンシパル、入力ハッシュ、プロファイル、プロバイダー ID（存在する場合）を保持します。
2. そのプリンシパルで `review_status` を照会します。転送障害後に `not_found` が返っても、それだけでは新しい ID を送信する十分な証拠にはなりません。まずサーバーでの処理と元のリクエストを照合してください。
3. プロバイダーのプロジェクト使用量とリクエストの診断情報を比較します。`store:false` ではレスポンスの取得が利用できない場合があり、レビューの再取得は保証されません。
4. 独立した証拠を持つ運用者だけが、該当する正確な `(principal, request_id)` 行を更新し、照合済みの終了状態に設定してください。信頼できる使用量が別の請求額を裏付けない限り、課金額または予約額を保持します。アプリケーションにはリセット、返金、削除のツールはありません。証拠は非公開で記録してください。結果不明の実行を、黙って新しい有料呼び出しに置き換えてはいけません。

予約は照合後も含め、元の UTC 送信日と送信月に計上されます。日付や月の境界を越えても、結果不明の同時実行数はリセットされません。リクエスト金額は、日次と月次の合算上限の残額を超えられません。レート制限は新規に予約されるレビュー ID（設定例では 100 件/日）に適用され、無料のメタデータ呼び出しには適用されません。必要に応じて、ネットワーク側にも不正利用対策を設けてください。

## アップグレード

`npm ci`、型チェック、ビルド、テストを実行します。まずマイグレーション SQL を確認し、同じ D1 データベースに新しいマイグレーションを適用してから、非公開設定でデプロイします。既存の `(principal, request_id)` 行はアップグレード後も保持しなければなりません。許可リスト内のプロファイルを変更しても、完了済み ID は再実行されません。新しい ID は、照合後に意図して新しいレビューを実行する場合だけに使ってください。プリンシパル ID を変更すると、既存のステータス行にアクセスできなくなるため、Bearer トークンのローテーション時も ID を安定させてください。

## ローテーションと削除

トークンをローテーションするには、新しいランダム値を生成し、`AUTH_TOKENS` 内の該当プリンシパルのダイジェストを置き換えてから、許可されたクライアントのパスワードマネージャーに基づく設定を更新します。単にトークンをローテーションするためにプリンシパル ID を変更しないでください。OpenAI キーのローテーションでは `OPENAI_API_KEY` だけを更新します。共有キーの他の利用元については、別途調整が必要です。新規リクエストを停止するには Worker を削除します。D1 を別途削除する前に台帳をエクスポートして確認してください。削除は元に戻せず、重複排除の履歴が利用できなくなります。

## ローカル復旧と限定的な容量追加

1. MCPホストを停止しrebut status REQUEST_IDで元要求を確認し、再送しません。
2. 閉じた台帳と設定をバックアップし、可能なプロバイダー証拠を確認します。budget_reserved_microusd／budget_accounted_microusdはアプリの会計値で、unknownの確定請求額ではありません。
3. 不確かな場合は行・全額会計予約・元IDを保持し、未課金扱い・削除・完了結果の捏造をしません。
4. 保持する会計額を明示的に受け入れた運用者は、意図した新規レビュー用に容量を追加できます。1件が既定の1枠を占める場合、rebut set max-concurrent 2で1枠追加します（1–10）。旧枠解除・返金・元入力の再試行許可ではありません。
5. MCPホストを再起動します。日・月・要求上限は総会計額に引き続き適用します。実際の精算には独立証拠と対象行の運用者確認が必要で、自動化しません。

IDを失った場合はrebut status --pendingから始めます。キー／プロバイダー呼び出しなしで最大100件のローカルreserved/unknownメタデータを表示し、続きはhas_moreで示します。診断スナップショットで、新たな有料実行の許可ではありません。待機行がなくても金額／日次件数上限でlimit_exceededとなる場合があります。

容量上限は10です。すべて不確かな場合は、履歴削除や未課金扱いをせず、証拠に基づく運用者精算まで停止します。独立確認で精算後は通常の容量（既定1）に戻して再起動します。

既存カスタム値に例の2を上書きせず、待機件数と明示的に許可する新規並列数の合計で容量を選びます（最大10）。容量／予算コマンドはローカル制限全体のスナップショットを保持します。元IDが不明なら手順1の前にstatus --pendingを実行してください。

## メンテナーによる npm 公開

手動の `publish.yml` は保存した npm トークンを使わず、OIDC Trusted Publishing で公開します。main からのみ実行でき、安定版タグはワークフローのソースコミットと一致する必要があります。GitHub Environment `npm` で所有者 `abruption` が承認します。ビルドとテストには OIDC 書き込み権限がなく、検証済み tarball の公開ジョブだけに付与します。PR のマージや GitHub Release イベントによる自動公開は行いません。公開後にレジストリ処理や検証が失敗した場合は、再実行前に元の実行と成果物を確認します。Worker のデプロイや既存クライアントの更新は含みません。[メンテナー向けリリースチェックリスト（韓国語）](../../releases/release-checklist.ko.md#github-actions-trusted-publisher)に設定と操作の手順があります。初回利用前にワークフローのマージと npm trust の登録が必要です。
